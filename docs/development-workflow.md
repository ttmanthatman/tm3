# 需求驱动的开发流程

适用于“用户描述效果，执行者负责开发”的协作方式。目标是减少无关阅读、重复推理和重复检查；不承诺固定额度或节省比例。根目录 `AGENTS.md` 是执行入口，本文定义本地交付的验证规则；旧审计记录中的“每次提交全量检查”不再作为普通本地提交的默认要求。

## 从需求到交付

1. **确定结果**：用一两句话说明要实现的效果。执行者自行选择文件、实现方案与测试；只有影响产品结果的歧义或确实缺少授权时才询问用户。
2. **确定边界**：查看 Git 状态、最近提交和目标目录规则，记住本次起点。已有无关改动可辨认且不冲突时保留并继续。本地提交不需要查询远端；需要隔离时先选定最终工作树，再开始验证。
3. **就近定位并修改**：优先查图谱中的相关符号及调用者，只读必要源码。工具不可用时窄范围搜索，不反复修工具。小改动不自动扩展到全仓审计、重构、联网研究或多代理评审。
4. **按风险验证**：开发中先跑能验证本次行为的最小检查；最终选择下表中的检查。已经通过且对应代码、依赖、环境没变的结果可以复用，不为提交动作本身重跑。
5. **完成授权动作**：提交时只暂存本次完整改动，审阅 diff，再本地提交。推送、部署、版本更新仍各自需要相应授权。汇报效果、检查结论、提交号和必要的未验证项，避免要求用户阅读长日志。

## 最小上下文工作法

| 阶段 | 默认只带入的内容 | 何时扩大范围 |
| --- | --- | --- |
| 开工 | Git 状态、任务起点、适用规则、可观察结果 | 已有改动与任务重叠，或产品目标有实质歧义 |
| 定位 | 相关符号/路径、必要调用者、邻近测试 | 涉及共享契约、跨模块状态或图谱覆盖缺口 |
| 实现 | 当前源码片段、已确认约束、最小差异 | 证据表明当前边界不足以完成需求 |
| 验证 | 风险级别、选定命令、退出码、相关失败 | 新风险、真实失败，或下方矩阵要求全量 |
| 交付 | 修改文件、有效检查、剩余风险 | 用户要求解释，或确有交接需要 |

- 同一会话中未变化的规则、源码和结论直接复用；更新后只重读变化部分。代码检索按根 `AGENTS.md` 从 codebase-memory MCP 开始，具体查询与覆盖步骤由已安装技能维护，不在仓库另设一套启动流程。文档、配置直接查文本；源码回退按技能的覆盖缺口与工具可用性规则执行。
- 独立查询合并调用；搜索先限制目录、文件类型和返回范围，再按结果缩小。先找标题/符号，再读片段，避免整份索引、变更日志或测试输出进入上下文。
- 常规任务把简短计划留在会话内；只有委派、跨会话或高风险任务使用[任务卡](task-cards.md)。已有任务卡或交接摘要直接更新，不另建同内容文档。任务所需的最小信息随委派传递，不默认复制整段聊天。
- 不以省 token 为由跳过适用规则、调用者/覆盖核对或风险检查；也不为凑固定流程做无关阅读和验证。文本篇幅可比较，实际 token 随任务和工具输出变化，不承诺固定节省比例。

## Codex 与 Zcode 跨设备协作

两端共用根目录 `AGENTS.md`、目标目录的同名规则和本文。若所用工具没有加载仓库规则，开工提示中明确要求先读这些文件；不维护两套容易漂移的规则。`AGENTS.local.md` 只记录当前机器的路径、运行方式和私有约束，每台设备单独维护。

默认采用**一个任务、一端负责、完成后接力**。另一端需要同时做独立任务时，使用独立分支和独立 checkout/worktree，先约定文件边界与集成顺序。新任务分支默认使用 `codex/<任务名>`，用户指定的命名优先；分支名称不限制由哪个工具继续开发。同一任务或共享入口文件的修改串行进行。

### 开工与同步

每个设备保留独立 Git checkout，通过同一个远端交换代码；避免用网盘实时同步正在使用的工作目录和 `.git`。开工先确认当前目录、分支、工作区改动和上次交接记录，再运行：

```sh
npm run dev:status
# 新任务开始或接收另一端已推送的工作时，在干净且已有上游的分支执行
npm run dev:sync
```

- `dev:status` 只读本地 Git，显示分支、提交、上游、领先/落后和未提交状态；领先/落后依据本地缓存，不表示已经查询远端。
- `dev:sync` 不依赖 `node_modules`，从当前分支配置的上游远端拉取引用，只允许快进；不假定远端叫 `origin` 或分支叫 `main`。
- 有已暂存、未暂存、未跟踪文件，分支领先或分叉，detached HEAD、缺少上游、Git 操作尚未结束，或 fetch 失败时，命令拒绝更新代码。保留现场，由执行者说明原因和集成方案；不自动 stash、reset、clean、rebase、提交或推送。
- 新任务分支先从已同步的主线创建；已有任务分支同步自己的上游。同步任务分支不等于集成最新主线；需要集成时单独审阅和验证，不把快进命令当作自动合并工具。
- 同步后若 `package-lock.json` 改变，运行 `npm ci`；依赖未变且安装有效时复用。需要时运行 `npm run prisma:generate`。数据库更新仍按迁移规则和本机说明单独执行。
- 继续当前尚未完成的本地任务时，不强制拉取另一端改动；先保持任务边界。不要在两个设备同时继续同一任务后再尝试用强制推送覆盖。

### 交接与交付

由执行者更新同一份[简短任务卡](task-cards.md#简短模板)交给下一端，无须再建台账。记录只含公开安全的项目上下文，不含账号、密钥、真实聊天或本机绝对路径；跨设备时补充分支、当前 SHA 和已核对的远端 SHA，尚未推送则明确写“仅本地，另一端尚不可获取”。

接收端先 fetch 并确认拿到交接 SHA，再继续；核对适用的本机规则和依赖，不假定聊天历史、图谱缓存或私有脚本会随 Git 传递。未提交的改动和未推送的提交仍只在原设备可见。需要提交或推送而尚无授权时，先把改动与验证整理到可审阅状态，明确交接尚未上传；不声称另一端已经可用。

验证结果绑定到代码、依赖和环境。同一工作区未变的结果可以复用；换设备后至少确认依赖和基线、运行相关定向检查。跨多个提交验收使用 `verify:changed -- --base <任务起点SHA>`，避免刚提交后空 diff 漏检。推送前在最终树运行一次 `verify:full`；不用为了交接先重复运行全部领域套件。

Git 只同步源码和公开说明。`.env*`、`AGENTS.local.md`、`.codex/`、数据库、上传文件及 `output/` 按忽略规则留在各自环境；数据复制、部署、发布仍单独授权。共享数据库或端口的同机双 checkout，切换运行端时按私有本机说明先停止原端，再启动接收端。

## 验证选择

| 改动类型 | 本地完成要求 |
| --- | --- |
| 纯文档、开发说明 | `check:public-tree`、检查修改的链接和 `git diff --check`；README 等受管理文件还需 `check:release` |
| 已有界面的局部文案、样式或单领域低风险修复 | `verify:changed` 选择的领域检查；受影响的生产构建；变更行为的针对性验收；public-tree 与 diff 检查 |
| 常规单领域功能 | 领域类型、测试与构建，相关行为验收；可由 `verify:changed` 加必要的构建覆盖 |
| 独立静态原型 | 原型自身语法/交互检查、适用的浏览器验收、public-tree 与 diff 检查；不能声称生产功能已完成 |
| 数据库、认证权限、消息一致性、文件存储、Service Worker、跨领域契约、架构或验证基础设施 | `verify:full`，以及相关隔离 E2E、迁移或安全场景检查 |
| 依赖、锁文件、构建/TypeScript 配置、CI、无法判断影响范围的改动 | `verify:full`；不得通过排除不认识的文件规避回退 |
| 推送、发布准备、CI，或明确要求完整验证的交接 | 最终树上一次 `verify:full`，外加适用的 E2E/迁移检查；复用同一树已有有效结果 |

`verify:changed` 按路径保守选领域，不懂业务风险；执行者必须先判断风险。例如单个认证文件仍需全量验证。它不会自动运行普通客户端构建、所有浏览器测试或迁移验证，不能将其通过描述成“全量通过”。`verify:full` 已包含 lint、类型检查、所有源码测试组和生产构建，不要在它之前逐一再跑这些完整套件。

UI 改动先验收受影响流程：一个手机和一个桌面尺寸；涉及 Safari、触摸、阅读器或跨浏览器行为时加 WebKit 及相关模式。遵守模块已有回归要求，只有新增风险或失败才扩大矩阵。不要为同一结论反复截图，也不要把模拟视口说成真机测试。登录、频道导航、消息持久化、圣经阅读、管理账号仍须运行相关隔离 E2E。

## 避免无关文件触发全量检查

默认 `verify:changed` 包含工作区所有改动和未跟踪文件，适合单一任务的干净起点。先预览选择：

```sh
npm run verify:changed -- --dry-run --quiet
```

已有无关的未跟踪原型时，在审阅范围后，显式暂存本次所有文件（包括新文件、测试和文档），再使用：

```sh
git add -- <本次文件1> <本次文件2>
npm run verify:changed -- --staged --quiet
```

- `--staged` 只选择暂存区相对 HEAD 的改动；不与 `--base` 混用。先检查暂存区，不能混入用户已有的暂存内容。
- 检查仍运行于工作目录。为避免结果和提交内容不一致，有已跟踪的未暂存改动时会拒绝执行；不要为了通过而暂存无关内容，需要时使用隔离工作树。
- 无关未跟踪文件不会参与选择，但仍可能被构建、测试或导入读取。发现这种关联时必须纳入任务或隔离；`--staged` 不是隔离执行环境。
- 公开树检查读取 Git 已跟踪/已暂存文件；交付的新文件必须纳入暂存或直接检查，不能因为未跟踪就声称已经扫描。
- 暂存后若又修改了内容，应重新审阅并暂存，重跑受影响的检查。跨提交验收用 `--base <本次起点>`；没有选中检查不是通过。
- 原型属于任务本身时不能用 `--staged` 把它排除。独立静态原型按上表专项验收；默认脚本对未知文件仍保守回退全量。

## 控制输出与返工

- `--quiet` 省略逐文件列表，保留范围、检查命令、回退原因和结果；`--dry-run` 只预览，不算验证。
- 验证子命令的完整输出存入系统临时目录；成功显示结果，失败最多回传末尾 6000 字符和日志路径。诊断时先找相关错误，不把完整日志反复放入上下文。需要长期保留的证据另存到忽略目录。
- 直接运行长检查时也应保留真实退出码，不使用会掩盖失败的 `command | tail`。
- 小任务默认一个执行者，不产生额外任务卡、评审会话或设计文档。需要跨会话交接、独立并行工作或高风险变更时才使用简短任务卡。
- 同一故障两次修复失败后停止盲试，保留复现和证据，说明具体阻碍与可执行下一步。
- 上下文过长需要交接时，只携带目标、基线、修改文件、已通过检查和待解决事项，避免重新讲述完整历史。
